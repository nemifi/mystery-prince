# Experience Core and Contract

Status: WORKING

## Core principle

EXPERIENCE defines what must be true for a work to remain itself. Runtime decides how the user experiences those truths.

## EXPERIENCE CORE

The initial semantic core should be limited to:

- Premise: what kind of work this is.
- Casting: which PRINCE appears as which ROLE in this work.
- Truth: what actually happened in the fictional situation, including critical causal relationships.
- Player Question: what the user is fundamentally trying to discover, understand, or decide.
- Dramatic Spine: the essential sequence of perception changes that gives the work its intended dramatic identity.

These are semantic concepts, not screen structures.

## Canon policy

### Hard Canon
Changes normally create a new EXPERIENCE:

- core premise
- principal cast/role identity when it materially changes the work
- culprit/cause/truth
- critical causal relationships
- central mystery
- final meaning or resolution

### Adaptive / Soft Canon
A REALIZATION may vary these within an experience-specific adaptation policy:

- discovery order
- hint density
- optional interactions
- dialogue wording
- pacing
- some misdirection presentation
- optional scenes

### Presentation
Runtime owns presentation details such as text, voice, 2D/3D, input method, camera, animation, interface layout, and future interaction technology.

## EXPERIENCE CONTRACT

The contract between creation and runtime should describe semantic meaning rather than current UI.

The contract may express:

- Entities: people, objects, places, events, claims, evidence, concepts.
- Facts: propositions that are true, false, uncertain, observed, hidden, or inferred.
- Knowledge: who knows what and what the player currently knows.
- Relations: contradiction, support, cause, ownership, location, timing, implication, etc.
- Opportunities: what meaningful interaction is currently available.
- Consequences: what semantic state changes after an interaction or inference.
- Completion Conditions: what constitutes resolution of the experience.
- Required Capabilities: what the runtime must be able to let the player do.
- Adaptation Policy: what the runtime may vary.

The contract must not contain UI coordinates, dialogue-box assumptions, sprite instructions, button names, framework-specific objects, or model-specific prompts.

## Compatibility principle

Universal compatibility is not required. An EXPERIENCE may require capabilities unavailable to an older runtime. The goal is extensible compatibility, not a lowest-common-denominator format.
