# Current Product Thesis

## Status

Working thesis. This is intentionally broader than the MVP specification.

## Thesis

> **MYSTERY PRINCE is a platform for continuously delivering and evolving interactive mystery experiences centered on attractive male characters.**

The platform is designed to survive changes in AI capability, interface technology, content format, device, and runtime architecture.

## User-facing value hierarchy

### 1. Character attraction
The first hook is a compelling male character: "I want to know more about him."

This does not require romance, ownership, progression, or a fixed relationship model.

### 2. Mystery participation
The user experiences the character through mystery: suspecting him, trusting him, being deceived by him, discovering his role, or uncovering what is hidden.

Mystery must retain intrinsic entertainment value. It is not merely a wrapper for character promotion.

### 3. Platform variety
The long-term reason to return is the expectation of new combinations:

- new PRINCES
- familiar PRINCES in new ROLEs
- new mystery structures
- new worlds
- new interaction formats
- future AI-native experiences

## What is intentionally not fixed

MYSTERY PRINCE is not permanently defined as:

- an otome game
- a visual novel
- a 30-minute game
- a fixed-cast story universe
- a character collection game
- an AI-generation product
- a chat game
- a 2D mobile game

Any of these may exist as implementations or experience types without becoming the platform identity.

## PRINCE definition policy

PRINCE should remain deliberately broad.

It is a brand label for male characters presented by MYSTERY PRINCE as compelling central figures. It is not a rigid in-world category, species, profession, morality type, or story role.

Over-defining PRINCE would reduce future casting and collaboration freedom.

## Initial implementation principle

The MVP should implement only what is necessary to validate the platform's core value.

Future extensibility should be preserved in architecture and data boundaries, not by prematurely implementing future-facing features.

> **Design for extension; build only what is needed now.**
